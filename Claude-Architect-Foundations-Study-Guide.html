⚠️ Core Exam Philosophy
The exam's defining theme: LLMs are probabilistic. Critical business logic must be enforced deterministically in code (hooks, gates, schemas) — not in prompts. When a question asks "most effective," look for the architectural/programmatic solution over the prompt-based one.
✅ When prompt-based IS correct
Calibrating escalation decisions · Teaching tool selection for ambiguous cases · Communicating output format · Reducing false positives in reviews
⚠️ When programmatic IS correct
Enforcing tool ordering for financial operations · Blocking policy violations above threshold · Loop termination logic · Data format normalization

Agentic Architecture & Orchestration

🔄 Agentic Loop Lifecycle TS 1.1
🎯 What the exam tests
How to correctly implement loop control flow using stop_reason. Recognising anti-patterns that terminate loops incorrectly.

The Loop Cycle:

  1. Send messages + tools to Claude API
  2. Inspect stop_reason in the response
  3. If "tool_use" → execute the requested tools, append results to history, go to step 1
  4. If "end_turn" → present final answer, terminate loop
stop_reasonMeaningAction
"tool_use"Model wants to call a toolContinue — execute tools, return results
"end_turn"Model has finished respondingTerminate — return answer to user
⚠️ Anti-Patterns (exam distractors)
  • Parsing text for "I'm done" / "Can I help with anything else?" — never do this
  • Setting an arbitrary iteration cap (e.g., max 10 loops) as the primary stopping mechanism
  • Checking if assistant response contains text content as a completion signal
✅ Correct pattern
Tool results must be appended to conversation history between iterations so the model can incorporate new information into reasoning.
🕸️ Multi-Agent Coordinator–Subagent Pattern TS 1.2 & 1.3
🎯 What the exam tests
Diagnosing why multi-agent output is incomplete. How context passes between agents. Parallel vs sequential execution. The Task tool requirement.

Hub-and-spoke topology:

  • Coordinator owns: decomposition, delegation, aggregation, error routing
  • All inter-subagent comms flow through the coordinator (not peer-to-peer)
  • Subagents have isolated context — they do NOT inherit coordinator history automatically

Spawning subagents:

  • Uses the Task tool
  • allowedTools must include "Task" for coordinator to spawn subagents
  • Parallel execution: emit multiple Task calls in a single coordinator response (not separate turns)
⚠️ Classic Exam Trap: Overly Narrow Decomposition
Scenario: System researches "AI impact on creative industries." Subagents run successfully. Output only covers visual arts.
Root cause: Coordinator decomposed topic into "AI in digital art / graphic design / photography" — completely missing music, writing, film.
Subagents executing correctly ≠ system working correctly. The coordinator's scope definition is the bug.
✅ Context Passing Best Practice
Include complete findings from prior agents directly in the subagent's prompt. Use structured data to separate content from metadata (source URLs, doc names, page numbers). Do NOT rely on automatic inheritance.
Do ThisNot This
Pass web search results + doc analysis directly in synthesis subagent promptAssume subagent can "see" what coordinator found
Emit multiple Task calls in one coordinator response for parallelismSequential turns to spawn each subagent
Coordinator prompts specify goals and quality criteriaStep-by-step procedural instructions (reduces adaptability)
🔒 Programmatic Enforcement vs Prompt-Based Guidance TS 1.4 & 1.5
🎯 What the exam tests
When to use hooks vs prompts. How to block tool ordering violations deterministically. SDK hook types.
⚠️ Prompts are probabilistic
"Always verify customer before processing refund" = non-zero failure rate. Unacceptable for financial operations. Will occasionally be skipped.
✅ Hooks are deterministic
Prerequisite gate: programmatically block process_refund until get_customer returns a verified ID. 100% enforcement.

Agent SDK Hook Types:

HookUse For
PostToolUseIntercept tool results before model processes them — normalize heterogeneous data formats (Unix timestamps → ISO 8601, numeric codes → labels)
Tool call interceptionIntercept outgoing tool calls — block policy-violating actions (e.g., refunds > $500) and redirect to escalation workflow
Prerequisite gatesBlock downstream calls until prerequisites complete (e.g., block lookup_order until verified customer ID exists)
📌 Structured Handoff on Escalation
When escalating to a human agent who lacks the conversation transcript, compile: customer ID · root cause · refund amount · recommended action. Don't assume the human can read the chat history.
🧩 Task Decomposition & Session Management TS 1.6 & 1.7
PatternUse WhenExample
Prompt chaining (fixed sequential)Predictable, multi-aspect tasks with known stepsCode review: per-file pass → cross-file integration pass
Dynamic adaptive decompositionOpen-ended investigation; subtasks depend on findings"Add comprehensive tests to legacy codebase" — map structure first, then prioritise

Why split large code reviews into passes? Prevent attention dilution — reviewing all files at once causes inconsistent depth, missed bugs, and contradictory feedback for identical patterns.

Session Resumption:

  • --resume <session-name> — continue named session
  • When resuming after file changes, explicitly tell the agent which files changed (don't force full re-exploration)
  • If prior tool results are stale: start a new session with a structured summary injected into initial context

Session Forking:

  • fork_session — create independent branches from a shared analysis baseline
  • Use when exploring divergent approaches (e.g., microservices vs in-place refactor) to prevent cross-contamination

📝 Tool Interface Design & Descriptions TS 2.1
🎯 What the exam tests
How to fix tool misrouting. What makes a good vs bad tool description. When to split vs consolidate tools. System prompt interactions.
⚠️ Root Cause of Tool Misrouting
Minimal descriptions ("Retrieves customer information" / "Retrieves order details") = LLM lacks context to differentiate. Tool descriptions are the PRIMARY selection mechanism.

A good tool description includes:

  • Core purpose (clearly differentiated from similar tools)
  • Expected input formats and identifier types
  • Example queries it handles
  • Edge cases and boundary conditions
  • Explicit: "use this instead of X when…"
⚠️ Too many tools = degraded reliability
18 tools instead of 4–5 increases decision complexity. Give agents only tools needed for their role. Synthesis agent should not have web search tools.
✅ Scoped tool access
Split generic tools into purpose-specific ones. Give synthesis agent a scoped verify_fact tool for simple lookups (85% of cases), route complex verifications through coordinator.
⚠️ Keyword-Sensitive System Prompts
If your system prompt contains "when user mentions 'account', check customer record first" — this can override perfectly good tool descriptions, creating unintended selection patterns. Audit system prompts for this.

tool_choice options:

ValueBehaviour
"auto"Model may return text OR call a tool (default)
"any"Model must call a tool (any it chooses) — guarantees structured output
{"type":"tool","name":"X"}Model must call the specific named tool — use for forced first-step ordering
🚨 Structured Error Responses for MCP Tools TS 2.2
🎯 What the exam tests
Error categorisation. Distinguishing access failure from empty result. Anti-patterns (silent suppression, generic status, full termination).

Error categories:

  • Transient — timeout, service unavailable (may retry)
  • Validation — invalid input format
  • Business — policy violation (e.g., refund cap)
  • Permission — access denied

Required error fields:

  • isError: true (MCP flag)
  • errorCategory (transient/validation/permission)
  • isRetryable: boolean
  • Human-readable description
  • Partial results (if any)
SituationCorrect Response
Timeout on web searchReturn structured error: failure type, attempted query, partial results, alternatives — let coordinator decide retry
Timeout after local retry exhaustedPropagate to coordinator with context; do NOT return generic "unavailable"
Query succeeds but returns 0 resultsNot an error — valid empty result. Mark as success. (Critical distinction!)
Policy violation (refund > $500)isRetryable: false + customer-friendly explanation + redirect signal
⚠️ Anti-patterns
  • Returning empty results marked as success (hides failure)
  • Terminating entire workflow on a single subagent failure
  • Generic "Operation failed" — prevents intelligent coordinator recovery

🎯 Explicit Criteria vs Vague Instructions TS 4.1
🎯 What the exam tests
Why "be conservative" fails. How to reduce false positives through specificity.
❌ Vague (fails)✅ Explicit (works)
"Check that comments are accurate""Flag comments only when claimed behaviour contradicts actual code behaviour"
"Be conservative, only report high-confidence findings"Define specific categories to report vs skip with examples for each
"Only report issues you're sure about"Define per-category criteria: bugs → always report; minor style → skip; local patterns → skip
⚠️ False positives destroy trust
High false positive rate in one category (e.g., style) undermines developer trust in all categories, including the accurate ones (security bugs). Strategy: temporarily disable the noisy category while improving its prompt.
📚 Few-Shot Prompting TS 4.2
🎯 What the exam tests
When few-shot is the right technique. What makes few-shot examples effective. When NOT to use it (wrong tool for the job).

Few-shot is most effective for:

  • Ambiguous cases where the reasoning needs to be demonstrated (not just the answer)
  • Consistent output formatting when instructions alone produce inconsistency
  • Handling varied document structures (inline citations vs bibliographies)
  • Reducing extraction hallucination for informal measurements and non-standard formats
  • Calibrating escalation decisions (show why case A escalates but case B doesn't)
✅ Effective few-shot structure
2–4 targeted examples · Cover ambiguous scenarios specifically · Include explicit rationale for why one action was chosen over plausible alternatives · Show desired output format
⚠️ Ineffective few-shot
Groups of clear, unambiguous examples (model already handles these) · Too many examples (token overhead without benefit) · Examples without reasoning
📌 Few-shot enables generalisation
Good examples teach the model to generalise judgment to novel patterns — not just match pre-specified cases. This is why targeted ambiguous examples outperform large banks of obvious examples.
🗂️ Structured Output via Tool Use & JSON Schemas TS 4.3
🎯 What the exam tests
tool_choice options. What JSON schemas prevent vs don't prevent. Nullable fields. Enum patterns.
✅ tool_use with JSON schema = most reliable structured output
Eliminates JSON syntax errors. Forces schema-compliant response. Do NOT use plain text "respond as JSON" — produces syntax errors.
⚠️ What JSON schemas DON'T prevent
Semantic errors still occur: line items that don't sum to total · values placed in wrong fields · dates formatted differently than expected. Use separate validation logic for these.
Schema PatternWhy / When
Nullable / optional fieldsSource document may not contain the info. If required, model fabricates values. Use nullable to get honest nulls.
Enum + "other" + detail stringExtensible categorisation without fabrication. Unknown values → "other" with description.
"unclear" enum valueAllows model to represent genuine ambiguity instead of forcing a guess

Extraction flow:

  1. Define extraction tool with JSON schema as input parameters
  2. Set appropriate tool_choice (see table above)
  3. Parse structured data from tool_use response block
  4. Run semantic validation (sum checks, cross-field consistency)
🔁 Validation, Retry & Batch Processing TS 4.4 & 4.5

Retry-with-error-feedback:

  1. Extract structured data
  2. Validate semantically
  3. On failure: resend original doc + failed extraction + specific validation errors
  4. Model self-corrects
⚠️ Retries won't fix this
If required info is simply absent from the source doc. Retrying is only effective for format mismatches and structural errors.

🔍 Multi-Instance & Multi-Pass Review Architectures TS 4.6
⚠️ Self-review limitation
A model retains reasoning context from code generation — less likely to question its own decisions. Using "review your own output carefully" is less effective than a fresh independent instance.

💾 Managing Long Conversation Context TS 5.1
🎯 What the exam tests
How to preserve transactional facts (amounts, dates) through summarisation. Lost-in-middle effect mitigation. Token efficiency.
⚠️ Progressive summarisation risk
Summarisation condenses "the 15% discount I mentioned" → "promotional pricing was discussed." Specific amounts, dates, order numbers, and customer-stated expectations are lost. Customers then reference exact numbers that the agent no longer has.
ProblemSolution
Transactional facts lost in summarisationExtract amounts/dates/order IDs into a persistent "case facts" block included in EVERY prompt, outside the summarised history
Verbose tool output consuming tokensTrim tool results to only relevant fields before they accumulate (e.g., 5 relevant fields from a 40-field order lookup)
Lost-in-the-middle effectPlace key findings summaries at the beginning of aggregated inputs; use explicit section headers
Multi-agent synthesis losing sourcesRequire subagents to include metadata (dates, source URLs, page numbers) in structured outputs
🆘 Escalation & Ambiguity Resolution TS 5.2
🎯 What the exam tests
When to escalate immediately. Why sentiment ≠ complexity. How to handle multiple customer matches.
TriggerAction
Customer explicitly requests a human agentEscalate immediately — no investigation attempt first
Policy gap or ambiguity (e.g., competitor price matching)Escalate — agent cannot decide unilaterally on policy-undefined scenarios
Agent cannot make meaningful progressEscalate
Customer frustrated but issue is resolvableAcknowledge frustration, offer resolution; escalate only if customer reiterates the preference for human
Complex case with available resolution pathDon't auto-escalate — attempt resolution first
⚠️ Unreliable escalation signals
  • Self-reported confidence scores (LLM can be confidently wrong)
  • Sentiment / frustration level (doesn't correlate with complexity)
  • Heuristics for multiple customer matches
✅ Multiple customer matches
When get_customer returns multiple results: ask for additional identifier (email, phone, order number). Do NOT select based on heuristics (e.g., "most recent order").
⚡ Error Propagation in Multi-Agent Systems TS 5.3

Key principle: Subagents should implement local recovery for transient failures. Only propagate errors that cannot be resolved locally — with full context of what was attempted and what partial results exist.

Anti-PatternWhy it Fails
Return generic "search unavailable"Hides context; coordinator can't decide intelligently between retry/alternative/partial
Terminate entire workflow on single failureUnnecessary; coordinator can often proceed with partial results
Mark failed empty result as successMasks failure; prevents any recovery
✅ Correct propagation pattern
Structured error: failure type + what was attempted + partial results + potential alternatives → coordinator decides: retry with modified query / alternative approach / proceed with partial data + coverage gap annotation
🗄️ Large Codebase Context & Information Provenance TS 5.4 & 5.6
ChallengeSolution

👁️ Human Review Workflows & Confidence Calibration TS 5.5
⚠️ Aggregate accuracy is misleading
97% overall accuracy can mask 60% accuracy on a specific document type or field. Always segment accuracy by document type AND field before reducing human review.

Human review routing workflow:

  1. Model outputs field-level confidence scores alongside each extraction
  2. Calibrate review thresholds using labeled validation sets (not guesswork)
  3. Route low-confidence + ambiguous/contradictory source documents → human review
  4. Run stratified random sampling of high-confidence extractions for ongoing error rate measurement
  5. Validate accuracy by document type and field before automating

Flashcards

Cover the answer, test yourself. These cover the most frequently tested concepts.

What does stop_reason = "tool_use" tell you to do?
Continue the loop. Execute the requested tools, append results to conversation history, and call Claude again with the updated context.
What does stop_reason = "end_turn" tell you to do?
Terminate the loop. Present the final answer to the user. Do NOT call Claude again.
An agent skips get_customer 12% of the time before calling process_refund. What's the correct fix?
Programmatic prerequisite gate. Block process_refund at the application layer until get_customer returns a verified customer ID. Prompt instructions have non-zero failure rate for critical business logic.
An agent calls get_customer when it should call lookup_order. Tool descriptions are minimal. First step?
Expand tool descriptions with input formats, example queries, edge cases, and explicit boundaries ("use lookup_order when given an order number"). Tool descriptions are the PRIMARY selection mechanism.
A multi-agent research system covers only visual arts when asked about "creative industries." All subagents ran successfully. Root cause?
Overly narrow task decomposition by the coordinator. The coordinator only assigned visual arts subtopics. Subagents executed their scope correctly — the bug is in what scope they were given.
How do subagents receive context in a coordinator-subagent pattern?
Explicitly, in the prompt. Subagents have isolated context and do NOT automatically inherit the coordinator's conversation history. The coordinator must inject all necessary context directly.
How do you spawn parallel subagents instead of sequential ones?
Emit multiple Task tool calls in a single coordinator response. If you spawn one per turn, they run sequentially. Single response = parallel execution.
What allowedTools setting does a coordinator need to spawn subagents?
allowedTools must include "Task". Without "Task" in allowedTools, the coordinator cannot invoke subagents.
A web search subagent times out. What should it return to the coordinator?
Structured error context: failure type + attempted query + any partial results + potential alternative approaches. Never return generic "search unavailable" — it prevents intelligent coordinator recovery.
What's the difference between a timeout error and a valid empty result?
Timeout = access failure, mark as error, coordinator decides on retry. Empty result = successful query that found nothing, mark as success. These are fundamentally different outcomes.
A custom /review slash command should be available to all developers who clone the repo. Where?
.claude/commands/ in the project repository. These are version-controlled. ~/.claude/commands/ is personal only and not shared via git.
A new team member isn't getting the coding standards. They use Claude Code on the project. Why?
The instructions are in user-level ~/.claude/CLAUDE.md (not version-controlled). Fix: move to project-level .claude/CLAUDE.md so it's committed to the repo and available to all team members.
Test files are spread across the codebase. You want test-specific conventions to apply automatically. Best approach?
.claude/rules/ files with YAML frontmatter glob pattern: paths: ["**/*.test.tsx"]. Applies conventions by file type regardless of directory location. Better than directory CLAUDE.md for cross-codebase file types.
Restructuring a monolith into microservices (dozens of files, service boundary decisions). Which Claude Code mode?
Plan mode. Complex tasks with architectural decisions, multiple valid approaches, and large-scale changes require exploration before committing. Direct execution risks costly rework from late-discovered dependencies.
A CI pipeline job hangs indefinitely waiting for Claude Code. Fix?
Add the -p (or --print) flag: claude -p "your prompt". This runs Claude Code in non-interactive mode — processes the prompt, outputs to stdout, exits without waiting for user input.
You want structured JSON output from Claude in a CI pipeline for automated PR comment posting. Flags?
--output-format json combined with --json-schema. Produces machine-parseable structured findings. Also use -p for non-interactive mode.
What's the most reliable way to guarantee schema-compliant structured output from Claude?
tool_use with a JSON schema as the tool's input parameters. Forces schema-compliant structure and eliminates JSON syntax errors. "Respond as JSON" in prompts still produces syntax errors.
What do JSON schemas via tool_use NOT prevent?
Semantic errors: line items that don't sum to totals, values placed in wrong fields, incorrect cross-field relationships. JSON schemas enforce structure, not logic. Use separate validation + retry-with-feedback for semantic correctness.
A required extraction field is sometimes missing from source documents. You're getting hallucinated values. Fix?
Mark the field as nullable / optional in the JSON schema. When required, the model fabricates values to satisfy the schema. Nullable fields return honest nulls when info is absent.
You want 50% API cost savings for a nightly technical debt report. Can you use the Message Batches API?
Yes. Batch API = 50% savings, up to 24-hour processing window, no latency SLA. Nightly reports are latency-tolerant. Would NOT work for blocking pre-merge checks where developers wait for results.
A 14-file code review produces inconsistent depth and contradictory feedback. How to restructure?
Split into focused passes: analyze each file individually for local issues → separate integration pass for cross-file data flow. Prevents attention dilution. Never use "3 independent passes, only flag consensus issues" — suppresses real bugs.
What is the PostToolUse hook used for?
Intercepting tool results before the model processes them — typically for data normalisation: converting Unix timestamps to ISO 8601, numeric status codes to labels, unifying heterogeneous formats from different MCP servers (including ones you can't modify).
context: fork in a skill's frontmatter — what does it do?
Runs the skill in an isolated sub-agent context. Verbose output (codebase analysis, brainstorming) won't pollute the main conversation. The main session stays clean; only the final result comes back.
Agent achieves 55% first-contact resolution (target 80%). Escalates simple cases, handles complex ones. Most effective fix?
Add explicit escalation criteria to the system prompt with few-shot examples demonstrating when to escalate vs resolve autonomously. Directly addresses the root cause: unclear decision boundaries.
A customer says "I want to speak to a human." Agent is mid-investigation of a simple issue. What should it do?
Escalate immediately. Explicit customer requests for a human must be honored without first attempting resolution. Do not complete the investigation and then escalate.
get_customer returns 3 matches. Agent picks the one with most recent order. 15% wrong account rate. Fix?
Ask the customer for an additional identifier (email, phone, order number) when multiple matches exist. Users have definitive knowledge of their identity. Heuristic selection is unreliable — one extra turn eliminates the error.
The word "account" in a message triggers get_customer 78% of the time. Tool descriptions are clear. Cause?
The system prompt contains keyword-sensitive instructions that steer behaviour based on "account" — overriding good tool descriptions. Audit and fix the system prompt.
Agent calls tools sequentially even when multiple are needed in one turn, causing 4+ loops per resolution. Fix?
Instruct Claude in the prompt to bundle related tool requests into a single turn. Claude natively supports multiple tool calls per turn. Prompting for this is the minimal architectural change that directly fixes the pattern.
Customers reference exact amounts ("the 15% discount") but the agent responds with wrong values. Why?
Progressive summarisation condensed specific numbers to vague descriptions. Fix: extract transactional facts (amounts, dates, order numbers) into a persistent "case facts" block included in every prompt, outside the summarised history.
When should you use fork_session?
When exploring divergent approaches from a shared analysis baseline (e.g., comparing microservices extraction vs in-place refactor). Prevents one exploration's context from contaminating reasoning about the alternative.
Overall extraction accuracy is 97%. Is it safe to reduce human review?
No. Aggregate accuracy masks poor performance on specific document types or fields. Validate accuracy by document type AND field segment. Use stratified random sampling to detect novel error patterns before reducing oversight.
Two credible sources report conflicting statistics on the same topic. What should synthesis do?
Annotate the conflict with both source attributions. Present both values with sources. Do NOT arbitrarily select one. Structure the report to distinguish well-established from contested findings. Let the coordinator reconcile.

📌 The Master Rule — Probabilistic vs Deterministic
Prompt instructions: probabilistic — appropriate for judgment calls, calibration, formatting, escalation criteria
Application-layer enforcement (hooks, gates, schemas): deterministic — required for tool ordering, policy thresholds, financial operations, data normalisation
When an exam question describes a compliance failure that has financial/legal consequences → always pick the programmatic/deterministic solution.
